# AiChatAssistant42 一般向け公開対応計画

## 目的
thch-vape.shop 固有実装を除去し、EC-CUBE 4.2 向けの汎用プラグインとして公開可能な品質に整える。

## BDDタスク一覧

### 0. 依存プラグイン削除（EasyArticle依存の完全削除） — 2026-09-01 経営者承認済み
- 方針: EasyArticle 依存は完全に削除する。graceful degrade ではなくコード・マイグレーション・ドキュメントから依存を除去する。
- 期待する振る舞い
  - 正常系: 記事系ツール/テーブル参照なしでも全チャット機能が 200 で動作する。
  - 異常系: 旧 EasyArticle テーブルが残っていても参照せず副作用なし。
  - エッジケース: 記事検索を期待する旧プロンプト/ツール定義が残存しない。
- 仕様データ例
  - `plg_ea_article` テーブル有無に関わらず chat API → 200 維持。
  - ツール定義から article 系 tool（get_articles / search_information 等の EasyArticle 起因）が削除される。
  - 移行: 既存環境の `plg_ea_article` が残っても本プラグインは無視する。


### 1. ドキュメント整合性の修正（README / ADMIN_MANUAL / USE_CASES）
- 期待する振る舞い
  - 正常系: README のディレクトリ構成・ルート数・導入手順が実装と一致し、初回導入者が手順どおりに設定完了できる。
  - 異常系: ドキュメント記載のパス不一致（例: `Resource/public`）があっても、修正後は存在する実パス（`Resource/assets`）のみ案内される。
  - エッジケース: 旧版情報を参照する利用者向けに、後方互換注意（旧記載との差分）を明記する。
- 仕様データ例
  - README 記載 `Tests/` → 実体なしの場合「現状のテスト方針」に置換。
  - ルート数は `routes.yaml` の実数に合わせる。

### 2. 固有ドメイン/ブランドの設定外部化（汎用化）
- 期待する振る舞い
  - 正常系: ショップURL・ショップ名・固定文言は `BaseInfo` または設定値から解決され、任意ECサイトで自然文言になる。
  - 異常系: `BaseInfo` が未設定でも、汎用フォールバック（例: `このショップ`）で動作し、特定ドメインが露出しない。
  - エッジケース: 既存環境で明示的に固有文言を使いたい場合、管理画面設定で上書き可能。
- 仕様データ例
  - 旧: `https://www.thch-vape.shop/products/detail/{id}`
  - 新: `{{ shop_url }}/products/detail/{id}` を動的生成

### 2.1 ハードコード棚卸し（コード + ドキュメント横断）
- 期待する振る舞い
  - 正常系: ドメイン固定、`admin-dev` 固定、User-Agent 固定、固有ショップ文言の露出箇所を一覧化し、置換対象を明確化する。
  - 異常系: 置換漏れがあった場合でも、検収チェックで再検出できる。
  - エッジケース: 運用上必要な固定値（ライセンス表示等）は「維持対象」として誤置換を防ぐ。
- 仕様データ例
  - 固定キーワード検出: `thch-vape.shop`, `admin-dev`, `User-Agent`, `リキッド通販ショップ`。
  - 検出パターン拡張:
    - URLハードコード: `https?://` を起点に固定URL抽出
    - 固定メール/ドメイン: `@` を含む固定値抽出（例: fallback from）
    - 固有名詞: 商品/人物/運用固有語を説明文から抽出
  - allowlist（維持対象）を先に定義: ライセンス表記、OSS参照URL、ベンダー公式URL。
  - 受け入れ: allowlistを除き、コード + ドキュメント横断で固有表現残存 0 件。

### 3. レート制限仕様の是正（セッション/クライアント単位）
- 期待する振る舞い
  - 正常系: 同一セッションの短時間連投で 429 となる。
  - 異常系: 単一クライアントの過負荷が他クライアント全体に波及しない。
  - エッジケース: `rateLimitPerMinute <= 0` の場合は無制限として扱う。
- 仕様データ例
  - 入力: 1分以内に同一 `session_id` で 20回（閾値10）→ 11回目以降 429
  - 入力: Aクライアント高負荷 + Bクライアント通常利用 → Bは許可
  - 入力: 同一IPで複数 `session_id` 乱発 → IP閾値で429
  - 入力: 同一 `session_id` を別IPから利用（プロキシ配下想定）→ session閾値優先で429
- 実装方針
  - 制限キーを `session:{session_id}` と `ip:{client_ip}` で分離する。
  - 既存SQL集計の継続可否を比較し、第一候補は Symfony RateLimiter 再利用とする。
  - SQL継続案を採用する場合、`(session_id, created_at)` 複合インデックスを追加検討する。
  - 429レスポンスは原因識別可能なメッセージ（session超過 / ip超過）を返す。

### 4. 管理UIの公開品質改善（設定導線とエラーメッセージ）
- 期待する振る舞い
  - 正常系: APIキー未設定・モデル不整合時に管理者が次アクションを判断できるエラー文言が返る。
  - 異常系: 無効状態でAPI呼び出ししても、403と明示メッセージで終了する。
  - エッジケース: 旧モデルIDが定義外でも、設定画面で「旧モデル」として可視化される。
- 仕様データ例
  - provider=`gemini`, model=`gpt-4o` → 400 + モデル不一致メッセージ

### 5. 受け入れ検証シナリオ（公開前スモークテスト）
- 期待する振る舞い
  - 正常系: チャット成功、フィードバック投稿成功、メール返信依頼成功を確認。
  - 異常系: 不正リクエスト（message欠落、不正email、無効feedback）が適切に 400/409 を返す。
  - エッジケース: 低負荷/高負荷、設定無効、有効APIキーなしの境界挙動が定義どおり。
- 仕様データ例
  - `POST /api/ai-chat-assistant/chat` with `{}` → 400
  - `feedback=neutral` → 400
  - 同一 `session_id` の重複feedback → 409

### 6. シーム別テスト計画（自動化優先順位）
- 期待する振る舞い
  - 正常系: Unit / Integration / Web の責務分離が明確で、回帰時に原因箇所を特定しやすい。
  - 異常系: 依存テーブル欠落、APIキー未設定、モデル不整合、429系の契約を自動検知できる。
  - エッジケース: 既存テストが薄い状態でも最小API契約テストから段階導入できる。
- テストマトリクス
  - Unit: `ChatFlowService`（ルール判定、文脈組み立て、フォールバック文言）。
  - Integration: Repository層（URL生成整合、商品/チャットログ永続化）。
  - Web: `ChatApiController`（200/400/403/409/429/500契約）。
- 仕様データ例
  - EasyArticle依存削除後も chat API → 500にならない（テーブル不在を前提としない）。
  - provider/model不整合 → 400 + 想定メッセージ。
  - settings無効時chat API → 403。

## 実装制約
- 変更はプラグイン配下に限定し、EC-CUBEコアは編集しない。
- 既存の公開インターフェース（APIパス、主要JSONキー）は破壊しない。
- 文字化け修正時は UTF-8 統一を徹底する。
- URL生成はルート名/設定値優先（`admin-dev` や特定ドメイン直書きを禁止）とする。
